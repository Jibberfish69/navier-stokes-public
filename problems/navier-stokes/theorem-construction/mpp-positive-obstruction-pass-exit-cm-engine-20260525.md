# MPP Positive Obstruction Pass/Exit CM Engine

Date: 2026-05-25

Status: installed governing CM proof-engine note.

## Thomas Source Formulation

The proof is run by following the positive program until it reaches a real
obstruction. At that obstruction, split the situation into exactly two proof
branches:

```text
1. the obstruction fails in a way capable of producing a nonsmooth event;
2. the obstruction passes in a way that produces smooth continuation.
```

The CM move is not to prove the particular positive estimate by force. The CM
move is:

```text
if branch 1 happens, then that failure is outside the class membership object;
therefore the only legal in-class branch left is branch 2, regardless of which
lawful mechanism supplies the control.
```

## Governing Engine

Let `O` be an obstruction produced by the ordinary positive Navier-Stokes proof
program: a source-control wall, a packet-carrier wall, a participation tower
wall, a coherence/readout wall, or any later same-solution obstruction.

Do not replace `O` by a demand to prove one specific controlling estimate. First
split it:

```text
O_pass: the same solution keeps the service needed for continuation.
O_fail: the obstruction failure is strong enough to be offered as a finite
        nonsmooth terminal event.
```

The pass branch is the member branch:

```text
O_pass
=> retained same-fluid Part/Field service
=> Member(Q; O_NS^work)
=> smooth continuation by the installed membership readout.
```

The failure branch is the exit branch:

```text
O_fail offered as the finite nonsmooth terminal event
=> CM-test-admissible same-solution terminal obstruction
=> first failed Part/Field service
=> Exit(Q; O_NS^work):=not Member(Q; O_NS^work).
```

Thus the obstruction has no legal third branch of the form:

```text
the obstruction fails enough to witness nonsmoothness
and still remains an in-class continuation branch.
```

## Theorem `PositiveObstructionPassExitCMEngine.A`

For every same-solution obstruction branch generated by the positive
Navier-Stokes proof program, once the branch is interpreted through the CM
class-membership object, the branch is decided as follows:

```text
pass branch  => Member(Q; O_NS^work) => smooth continuation,
fail branch  => Exit(Q; O_NS^work)   => outside the in-class Clay branch.
```

Equivalently, the CM route does not need to know which particular positive
estimate ultimately supplies the pass-side control. It does need the fail side
to do real work: the failure branch must enter the CM terminal test and its
first Part/Field failure must be derived. "Capable of nonsmoothness"
is a trigger for that test, not the proof of `Exit(Q)`.

## What This Demotes

This demotes the recurring wrong target:

```text
prove the particular positive obstruction estimate directly before the CM route
can close.
```

That is a positive-program burden. It may be useful support, but it is not the
governing CM contrapositive engine.

This also demotes the opposite wrong shortcut:

```text
terminal Exit(Q) is a contradiction by itself.
```

The CM statement is sharper: terminal exit is the lawful classification of the
failure branch. Once the branch is classified as exit, it is no longer a legal
in-class Clay continuation branch. The in-class branch is the pass branch.

## Future Surface Rule

Every future Navier-Stokes theorem surface that reaches an obstruction must
record these four fields before setting a target:

```text
obstruction: what positive proof wall was reached?
fail_branch: what finite nonsmooth terminal event is this wall supposed to witness?
cm_exit_landing: where does that fail branch land in Part or Field?
pass_branch: what in-class service remains, without requiring a named estimate
             to be the unique mechanism of control?
```

If a surface skips the fail-branch CM landing and demands direct control of the
positive obstruction, it has drifted out of the CM proof engine.

If a surface skips the fail-branch CM landing and simply says "bad enough to be
nonsmooth, therefore Exit(Q)", it has also drifted. The Part/Field face is
the mechanism that earns the exit conclusion.

## Clay-Closure Boundary

The follow-up referee audit
`mpp-no-third-branch-clay-closure-audit-20260525.md` proves the in-class
no-third-branch theorem:

```text
pass => Member(Q) => smooth continuation,
fail => Exit(Q)  => not an in-class continuation branch.
```

That is the correct branch law. The remaining Clay-level burden is not to
control one favorite positive estimate. It is also not the theorem-sized slogan
`OriginalSmoothData => not GenuineCMExit(T_*)` inserted as a local lemma.

The noncircular continuation of this engine is obstruction-by-obstruction:
prove CM-test entry, derive the first Part/Field failure on the fail
branch, and keep the pass branch as the only in-class continuation branch. That
is the route that preserves Thomas's pass/fail idea without smuggling the whole
MPP into a renamed "remaining burden."
